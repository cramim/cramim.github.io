# A/B — דף וריאנט לשינויי חוויית משתמש

מסמך למפתחים. מסביר את התשתית שנוספה כדי לבדוק שינויי UX **בלי לגעת בדף הראשי**.

---

## 1. מה נוסף

ארבעה קבצים חדשים. שום קובץ קיים לא נערך.

| קובץ | תפקיד |
|---|---|
| `v2.html` | וריאנט של `index.html` (דסקטופ) |
| `v2-mobile.html` | וריאנט של `mobile.html` (מובייל) |
| `app/v2.js` | **כל השינויים בקוד נכתבים כאן** — מנוע הניסויים + ה-hooks. קוד ייצור |
| `app/v2-test.js` | תשתית דף הבדיקות בלבד: מפתח כניסה, `read_only`, ניתוב, תג, מסך חסימה. נטען רק ע"י `v2*.html` |
| `app/v2.css` | כל השינויים בעיצוב |

`index.html`, `mobile.html`, `admin.html`, `app/app.js`, `app/mobile.js`, `app/app.css`, `app/mobile.css` — **לא נגענו בהם**. אפשר לאמת:

```bash
git diff --stat        # ריק. רק ארבעה קבצים חדשים ב-git status
```

שני דפי הווריאנט זהים למקור שורה-בשורה, פרט לשלוש שורות ב-`<head>` ולמחלקה על `<body>`:

```html
<link rel="stylesheet" href="app/v2.css">
<script src="app/v2.js"></script>
<script src="app/v2-test.js"></script>   <!-- דפי הווריאנט בלבד, ותמיד אחרי v2.js -->
...
<body class="v2 v2_desktop">     <!-- או v2 v2_mobile -->
```

### ניסויים פעילים

| id | מה זה עושה | מצב |
|---|---|---|
| `category-home` | מסך ראשי של קטגוריות במקום פילטר הקטגוריה | פעיל |
| `last-year-category` | כרטיס נוסף: הפעילויות שנרשמנו אליהן אשתקד. תלוי ב-`category-home` | פעיל |
| `login-autofocus` | פוקוס אוטומטי על שדה הכניסה (דסקטופ) | כבוי |

### איך `last-year-category` משיג את המידע

הנתון לא קיים בקמפיין הנוכחי, אבל `load` מקבל `campaign_id` — ולכן קריאה שנייה עם הקמפיין הקודם מחזירה את ההרשמות של אותה משפחה אשתקד. **אין שום שינוי בשרת.** הקמפיין הקודם נגזר מ-`campaign_list` שבתשובה (המזהה הגבוה ביותר שקטן מהנוכחי), ולא מקודד קשיח.

הקריאה רצה ברקע אחרי הטעינה הראשית, עם `please_wait` מנוטרל כדי שלא תחסום את המסך, ומרעננת את הכרטיסים כשהיא חוזרת.

ההצלבה היא **על טקסט ולא לפי מזהה**: לכל קמפיין טאב פעילויות משלו, ולכן `activity_id` הוא מזהה בתוך השנה בלבד — פעילות 3 בתשפ"ו אינה פעילות 3 בתשפ"ז. פעילות שנרשמנו אליה אשתקד ואינה מוצעת השנה יורדת מהרשימה.

### עמודה Q — שם גנרי

אותה פעילות מקבלת לפעמים שם אחר בין השנים ("שישי הורים סבב 1" מול "שישי הורים נובמבר"), והצלבה לפי השם בלבד מפספסת אותה. **עמודה Q בטאב הפעילויות** (אינדקס 16, אופציונלית) מחזיקה שם גנרי; שם גנרי זהה בשתי השנים מגשר על הפער.

כל פעילות מיוצגת ב**קבוצת מפתחות** — `{השם, group_name אם יש, הגנרי אם יש}` — ושתי פעילויות תואמות אם יש חפיפה באחד מהם. מכאן:

- שורה שעמודה Q שלה ריקה מתנהגת **בדיוק כמו קודם**, כלומר הצלבה לפי השם
- מילוי הגנרי בשנה אחת בלבד לא יכול לשבור התאמה שעובדת היום — העמודה היא תוספת בלבד, אף פעם לא החלפה
- אפשר למלא את העמודה בהדרגה, שורה-שורה, בלי לדאוג לסימטריה בין השנים
- **המחיר:** שם גנרי זהה בטעות לשתי פעילויות שאינן קשורות יגרום להן להתאים זו לזו

אין שינוי בשרת. `load` עושה `getDataRange()` ומחזיר את השורה כולה, ולכן עמודה שנוספת בסוף הגיליון מגיעה מעצמה, ו-`app.js` קורא עד אינדקס 15 בלבד.

> ⚠️ **עמודות חדשות בסוף הטאב בלבד.** `load` מסנן `item[0] > 0`, שורת הכותרות נופלת בסינון והלקוח לא רואה אותה — ולכן אין שום דרך לזהות עמודה לפי שמה, וכל האינדקסים קשיחים. הכנסת עמודה באמצע מזיזה את `COL_GENERIC` ב-`v2.js` ואת כל `item[N]` ב-`app.js` וב-`admin.js`, ושוברת בשקט גם את האתר וגם את הדוחות.

הכרטיס לא מוצג כלל אם אין התאמות, אם המשפחה לא הייתה רשומה אשתקד, או אם הקריאה נכשלה. `?v2debug=1` ידפיס כמה מפתחות נמצאו, כמה פעילויות הותאמו, **וכמה ערכי Q נקראו בפועל בכל שנה** — זו הדרך המהירה לוודא שהעמודה אכן מגיעה מהשרת.

להשוואה מול המקור בכל רגע: `?v2=off`. לבדיקת ניסוי בודד: `?only=<id>`.

## 2. איך זה עובד

סדר הטעינה הוא מה שמאפשר את כל זה:

```
app.js  →  (mobile.js)  →  v2.js  →  v2-test.js    ← v2.js תמיד אחרי app.js, ולכן הוא מנצח
app.css →  (mobile.css) →  v2.css       ← v2.css תמיד אחרון, ולכן הקסקייד שלו מנצח
```

זו בדיוק הגישה ש-`mobile.js` כבר משתמש בה (`$.extend` על `app`) — לא המצאנו דפוס חדש.

### המלכודת שנוטרלה

`app.js` מסתיים ב-`$(app.start)`. jQuery שומרת את **מצביע הפונקציה המקורי**, ולכן דריסה של `app.start` בקובץ מאוחר יותר לא משנה כלום. הפונקציה הזו מפנה כל מכשיר נייד ל-`mobile.html` אלא אם ה-URL כבר מכיל את המחרוזת `mobile.html`.

המשמעות: הורה שנכנס מהטלפון ל-`v2.html` היה **נזרק אוטומטית ל-`mobile.html` המקורי** ויוצא מהניסוי בלי שאיש ישים לב.

שני מנגנונים סוגרים את זה, שניהם ב-`v2-test.js` וללא נגיעה ב-`app.js`:

1. `v2-test.js` בודק את סוג המכשיר בעצמו ומנתב `v2.html ↔ v2-mobile.html` — נשארים בתוך הווריאנט.
2. מיד אחר כך הוא מקבע את `js.is_mobile()` לערך שמתאים לדף הנוכחי, כך שה-handler הישן שכבר נלכד לוקח את הענף שרק קורא ל-`app.init()` ולעולם לא מפנה.

> ⚠️ **הדף הנייד חייב להישאר בשם שמסתיים ב-`mobile.html`.** הבדיקה ב-`app.js` היא `indexOf("mobile.html")`, ו-`v2-mobile.html` עומד בה. שינוי שם יחזיר את המלכודת.

בנוסף נדרסה `app.change_campaign` — במקור היא מנווטת ל-`index.html` / `mobile.html` בשם קשיח, מה שהיה מוציא את המשתמש מהווריאנט בכל החלפת קמפיין.

## 3. איך מוסיפים שינוי

בתחתית `app/v2.js`, בסעיף `EXPERIMENTS`:

```js
v2.add({
    id:    "activity-points-badge",              // kebab-case, אותיות קטנות בלבד
    title: "הדגשת מספר הנקודות בכרטיס הפעילות",
    on:    false,                                 // true = חי לכל מי שנכנס לווריאנט
    pages: ["desktop"],                           // אפשר להשמיט = שני הדפים
    apply:  function () { /* פעם אחת, ב-DOM ready */ },
    render: function () { /* אחרי כל app.rebuild */ }
});
```

**מתי `apply` ומתי `render`:**

| השינוי נוגע ב… | השתמש ב… |
|---|---|
| כותרת, מסך כניסה, תפריטים, פילטרים — DOM סטטי | `apply` |
| כרטיסי פעילות, הרשימה של המשפחה, מד ההתקדמות | `render` |

`render` רץ אחרי כל `app.rebuild`, כלומר גם בטעינה וגם אחרי שמירה — התוכן הזה נבנה מחדש בכל פעם, ולכן `apply` לבדו לא יחזיק.

**לשינוי התנהגות ולא רק מראה:**

```js
v2.after("save",  function () { ... });
v2.before("login", function (uid) { ... });
v2.replace("filter", function (orig) {
    return function () { var r = orig.apply(this, arguments); /* ... */ return r; };
});
```

**עיצוב** — ב-`app/v2.css`, תחת בלוק עם אותו `id`. הקובץ נטען אחרון, ולכן דריסה בדרך כלל לא דורשת `!important`. יש לתחום כל כלל ב-`.v2` / `.v2_desktop` / `.v2_mobile`.

### שתי מוסכמות שכדאי לשמור

- **כל גוף ניסוי רץ בתוך `try/catch`.** ניסוי שנשבר מדלג על עצמו וחוזר להתנהגות המקורית, במקום להשאיר להורה מסך לבן. זה גם אומר שכדאי להסתכל ב-console אחרי שינוי — כשל *לא* יצעק בממשק.
- **אין לבנות HTML בשרשור מחרוזות.** ערכים שמגיעים מהנתונים מוזרקים דרך `.text()` / `.attr()` בלבד, כפי שנעשה בתג הצף. זו מוסכמה שנשמור בכל קוד חדש.

## 4. פרמטרי URL לבדיקה

| פרמטר | מה הוא עושה |
|---|---|
| `?v2=off` | מכבה את **כל** הניסויים בדף הווריאנט — בסיס להשוואה על אותו URL |
| `?only=id1,id2` | מריץ בדיוק את אלה, גם אם `on: false`. **זו הדרך להציץ בשינוי לפני שמפעילים אותו** |
| `?off=id1` | מריץ הכול חוץ מאלה |
| `?v2debug=1` | לוג מפורט ב-console |
| `?key=…` | מפתח הכניסה. ראה סעיף 6. נשמר ב-`sessionStorage`, ולכן נדרש רק בכניסה הראשונה בלשונית |

הפרמטרים מצטרפים לקיימים (`?campaign=`, `?mode=`, `?unlock=`).

בקונסול: `v2.list()` · `v2.active()` · `v2.enabled("id")` · `v2.refresh()`.

## 5. איך מריצים את הניסוי בפועל

### עכשיו — הצטרפות בקישור (מומלץ להתחלה)

שולחים לקבוצת בדיקה את `https://cramim.github.io/parents/v2.html?key=bdika2027`. אין שינוי בזרימה של אף אחד אחר, אין סיכון, ואפשר להפסיק בכל רגע בלי deploy — פשוט מפסיקים לשלוח את הקישור.

זו הסיבה שהתג הצף כולל קישור "לגרסה הרגילה" ו"משוב": מי שנתקע חוזר לבד, ומי שיש לו מה להגיד מגיע לטופס הקיים.

### כשתרצו חלוקה אוטומטית 50/50

זה **דורש שורה אחת בתוך `index.html`**, כלומר נגיעה בדף הראשי — ולכן לא נעשה עכשיו. כשתחליטו, זה הקוד:

```html
<!-- ב-index.html, לפני שאר ה-<script>ים -->
<script>
(function () {
    var KEY = "cramim-parents-ab";
    var b = localStorage.getItem(KEY);
    if (!b) { b = (Math.random() < 0.5) ? "a" : "b"; localStorage.setItem(KEY, b); }
    if (b === "b" && !/[?&]noab=/.test(location.search)) {
        location.replace("v2.html" + location.search);
    }
})();
</script>
```

השיוך נדבק ב-`localStorage`, כך שאותו הורה רואה תמיד את אותה גרסה. `?noab=1` מבטל.

⚠️ שימו לב לשתי נקודות לפני שמפעילים: זה מוסיף הפניה על הנתיב הקריטי של הדף הראשי, ו-`localStorage` נמחק כשהורה מנקה דפדפן או עובר מכשיר — אז אותה משפחה עשויה לקפוץ בין הגרסאות.

## 6. הגבלת גישה והגנה על הנתונים

שני מנגנונים, ששייכים לשתי בעיות שונות. שניהם ב-`config` בראש `app/v2-test.js`,
ולכן הם לא קיימים כלל בייצור — הקובץ הזה נטען רק בדפי הווריאנט.

### `read_only` — ההגנה האמיתית

```js
read_only: true      // ברירת מחדל
```

`app.post` היא הצינור היחיד של האפליקציה מול השרת, ולכן עטיפה אחת שלה חוסמת כל כתיבה מהדף — דסקטופ, מובייל, וכל זרימה עתידית. ההיתר הוא רשימה לבנה: רק `load` עובר, כל השאר נחסם ומציג הודעה.

**זו הנקודה החשובה:** דף הבדיקות פונה לאותו Apps Script ולאותו גיליון כמו האתר החי. בלי החסימה, כל הרשמה שנעשית תוך כדי בדיקה נכתבת לגיליון ההרשמות האמיתי ואי אפשר להבחין בינה לבין הרשמה של הורה. הגיליון כבר סובל משורות בדיקה ישנות שמעוותות דוחות — אין סיבה להוסיף עוד.

החסימה קורית **לפני** הקריאה המקורית, ולכן `please_wait` לא נדלק והממשק נשאר בדיוק במקומו.

מתי לכבות: כשתרצו שקבוצת הבדיקה תבצע דרך הווריאנט את ההרשמה האמיתית שלה. אז `read_only: false` — הנתונים אמיתיים, ההתנהגות אמיתית, ואין זיהום.

### `access_key` — מחסום, לא מנעול

```js
access_key: "bdika2027"     // הכניסה היא ?key=bdika2027
```

בלי המפתח הנכון הדף לא נטען כלל — `app.init` מנוטרל, אין פנייה לשרת, ומוצג מסך "דף בדיקות" עם קישור לאתר הרגיל. המפתח נשמר ב-`sessionStorage` אחרי כניסה מוצלחת, כך שהחלפת קמפיין או מעבר דסקטופ↔מובייל לא דורשים אותו שוב. הוא נמחק כשסוגרים את הלשונית.

⚠️ **צריך להיות ברור מה זה לא.** הבדיקה רצה בדפדפן והערך יושב ב-repo ציבורי. מי שפותח את `app/v2-test.js` או את כלי הפיתוח נכנס. זה עוצר הורה שקיבל את הקישור בהעברה ולא אמור להיות שם — זה לא עוצר אף אחד שמנסה.

זו בדיוק אותה חולשה שיש לסיסמת האדמין הקיימת, ולכן אין להסתמך עליה לשום דבר מעבר לזה. **ההגנה שבאמת מחזיקה כאן היא `read_only`**, כי היא מגינה על מה שבאמת יכול להינזק — הגיליון. גם מי שעוקף את המחסום לא יכול לכתוב.

להשבתה: `access_key: null`.

### `noindex`

שני דפי הווריאנט מכילים `<meta name="robots" content="noindex, nofollow">`, כדי שגוגל לא יציג אותם בחיפוש. זו לא הגבלת גישה אלא מניעת גילוי מקרי — וזה המקום שממנו מגיעה רוב התנועה הלא-מכוונת.

## 7. מדידה — מה אפשר ומה לא

זו נקודה שחשוב שתהיה ברורה מראש: **אין כרגע שום איסוף מדדים במערכת.** אין אנליטיקס, אין לוגים בצד הלקוח, וה-Apps Script לא מתעד אירועי שימוש.

מכאן שהשוואה כמותית אמיתית — "כמה אחוז מהמשפחות סיימו הרשמה בכל גרסה" — **אינה אפשרית בלי שינוי בשרת**, וזה בדיוק סוג השינוי שלא רוצים כרגע.

מה שכן אפשרי היום:

- משוב איכותני מקבוצת הבדיקה, דרך הטופס הקיים
- השוואה ידנית של מספר ההרשמות בגיליון לפני ואחרי
- מעקב מונחה: לשבת עם 3–5 הורים ולראות אותם משתמשים

כשתרצו מדידה אמיתית, הדרך הזולה ביותר היא `act_id` חדש שכותב שורות לטאב אירועים — הוספה נטו לשרת, בלי לגעת בזרימות הקיימות. אפשר לתכנן את זה בנפרד.

## 8. מגבלות ידועות

| נושא | פירוט |
|---|---|
| **כפילות HTML** | `v2.html` הוא עותק של `index.html`. עריכה של המקור **לא** תופיע בווריאנט. אין build step, ולכן אין דרך לשתף את ה-markup. אם יעברו שבועות עם שינויים במקור — יש לסנכרן ידנית (`diff index.html v2.html`) |
| **admin ו-friday** | לא נכללים. `admin.html` ו-`friday/` נשארו כפי שהיו |
| **z-index של התג** | `10000`, כי `mobile.css` מגיע ל-`9999`. גבוה מ-SweetAlert2 (`1060`), כלומר התג יופיע מעל דיאלוג. הוא קטן ובפינה, אבל אם זה מפריע — `v2.test.show_badge = false` ב-`v2-test.js` |
| **localStorage משותף** | שתי הגרסאות חולקות את `cramim-parents-user`, ולכן מעבר בין גרסאות לא מחייב כניסה מחדש. זה מכוון |
| **הגרשיים ב-`?only=`** | `js.urlParam` ממיר לאותיות קטנות, ולכן מזהי ניסויים חייבים להיות באותיות קטנות |
